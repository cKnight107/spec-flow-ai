# 架构边界约束

## 分层原则
- 上层可以依赖下层能力，下层不能反向依赖上层实现
- 业务应用不得绕过平台能力直接访问模型、知识源或企业系统
- 治理能力应横向复用，不得在各服务内重复造一套权限和审计逻辑

## apps 边界
- `portal-web` 面向最终用户，不承载治理策略实现
- `admin-console` 只负责配置、管理和运营视图
- `openapi-gateway` 只暴露外部接入能力，不承担核心领域逻辑

## services 边界
- `model-gateway` 统一承接模型调用，业务层不得直连厂商 SDK
- `retrieval-service` 统一承接检索，应用层不得自行拼装向量检索逻辑
- `tool-gateway` 统一承接工具接入与审计，Agent 不得直连企业系统
- `auth / policy / approval / audit` 负责治理能力，其他服务只消费统一接口

## packages 边界
- `packages/` 只能放可复用协议和无业务副作用代码
- 禁止在共享包中引入具体服务的运行时实现和基础设施细节

## integrations 边界
- 适配器负责协议转换，不负责核心路由、权限、审批或计费决策
- 外部厂商差异应封装在这里，避免污染服务核心代码

## 数据与配置边界
- 结构化元数据优先进入数据库模型
- 策略与路由优先进入 `configs/` 或治理服务
- 测试夹具进入 `tests/fixtures`，禁止混入生产配置
