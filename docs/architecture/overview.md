## 5. 技术架构设计

### 5.1 架构设计目标

本项目技术架构应围绕企业 AI 中台的整体目标展开：对上支撑多业务应用、多接入渠道，对中沉淀公共 AI 能力，对下屏蔽模型与数据源差异，并在横向具备权限、安全、审计、观测与成本治理能力。与此同时，平台需满足多模型、多知识源、多应用、多租户，以及从 RAG 问答逐步演进到任务自动化的建设目标。

结合文档提出的“复用优先、平台优先、数据优先、安全前置、分阶段建设、配置优先”等原则，技术架构建议采用 **TypeScript 全栈 + 平台内核自研 + Agent 运行时复用成熟框架** 的路线。也就是说，前后端与大部分平台服务采用 TypeScript 统一实现，而 Agent 执行、链路编排等运行时能力优先复用现有框架，中台重点掌控模型网关、知识治理、工具治理、权限审计与运营观测等企业级核心能力。

### 5.2 总体技术路线

推荐采用如下技术路线：

* 前端：**Next.js + React + TypeScript**
* 后端：**NestJS + TypeScript**
* Agent / Workflow 运行时：**LangGraph JS + LangChain JS**
* 数据层：**PostgreSQL + Redis + Object Storage**
* 检索层：**pgvector / Milvus + OpenSearch**
* 异步与任务：**BullMQ（MVP）/ Temporal（演进阶段）**
* 可观测：**OpenTelemetry + Prometheus + Grafana + Loki**
* 权限与治理：**SSO/OIDC + Casbin/OPA + Guardrails + Audit**

之所以推荐这条路线，是因为文档明确要求平台同时覆盖八大能力域，包括模型网关与路由中心、知识与记忆中心、智能体与工作流中心、工具与协议中心、PromptOps / EvalOps、应用交付、身份权限治理，以及观测运营与成本中心。单一 Agent 框架无法完整承接这些能力，尤其无法替代模型路由、权限继承、审计链路和成本治理等中台职责。

## 5.3 分层架构设计

文档已经给出平台的八层分层，因此技术实现上建议严格按照这八层落地。
```text
┌──────────────────────────────────────────────────────────────┐
│                        接入层 Access Layer                   │
│  Web Portal | Admin Console | OpenAPI | SDK | 企业微信/飞书/钉钉 │
└──────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│                     API Gateway / BFF 层                     │
│   鉴权接入 | 路由分发 | 流式输出 | 限流 | 渠道适配 | 会话入口        │
└──────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌───────────────┐    ┌────────────────┐    ┌────────────────┐
│ 应用交付中心   │    │ 智能体/工作流中心 │    │ Prompt/EvalOps │
│ App Service   │    │ Agent Runtime   │    │ Prompt/EvalSvc │
│ App Binding   │    │ Workflow Engine │    │ Playground     │
└───────────────┘    └────────────────┘    └────────────────┘
        │                     │                     │
        └──────────────┬──────┴──────────────┬─────┘
                       ▼                     ▼
              ┌────────────────┐    ┌────────────────┐
              │ 模型网关中心     │    │ 工具与协议中心   │
              │ Model Gateway   │    │ Tool Gateway   │
              │ Router/Policy   │    │ MCP/API/A2A    │
              └────────────────┘    └────────────────┘
                       │                     │
                       ▼                     ▼
              ┌────────────────┐    ┌────────────────┐
              │ 知识与记忆中心   │    │ 企业系统 / 外部能力 │
              │ RAG / Memory   │    │ CRM/OA/ERP/BPM │
              │ Retrieval      │    │ DB/API/MCP     │
              └────────────────┘    └────────────────┘
                       │
                       ▼
              ┌────────────────────────────────────┐
              │ 数据与存储基础设施                  │
              │ PostgreSQL | Redis | Object Storage│
              │ Vector DB | OpenSearch | MQ        │
              └────────────────────────────────────┘

──────────────── 横向治理与运营能力（全链路挂载） ────────────────
IAM/SSO | RBAC/ABAC | Guardrails | 审批 | 审计 | Trace | Metrics | Cost
```

这个图基本对应文档里的总体要求：
上面承接多渠道接入，中间沉淀公共 AI 能力，下面屏蔽模型、知识源和企业系统差异，横向补齐权限、安全、审计、观测与成本治理。文档也明确要求平台按接入层、应用层、编排与执行层、工具与协议层、知识与记忆层、模型服务层、控制与治理层、观测运营层来拆分。

### 5.3.1 接入层

接入层负责承接 Web、企业微信、飞书、钉钉、OpenAPI、SDK 等多种入口。技术上建议采用 Next.js 门户前端、NestJS API Gateway/BFF，以及 SSE 或 WebSocket 作为流式输出通道。这样既能支撑标准门户，也能支撑 IM 渠道与内嵌式组件。文档也明确要求应用支持 Web 门户、企业微信、飞书、钉钉、OpenAPI 和内嵌式组件等多渠道发布。

### 5.3.2 应用层

应用层负责把模型、Prompt、知识库、工具、工作流、安全策略和发布渠道装配为具体业务应用。这里建议自研 `App Service`，将应用定义为一套“绑定关系”而不是硬编码逻辑，使应用能快速复制与版本化发布。文档也要求应用具备创建、分类、配置、上下线、版本管理，以及模型、Prompt、知识库、工具、工作流/Agent、安全策略和发布渠道的绑定能力。

### 5.3.3 编排与执行层

编排与执行层负责 Workflow、Agent Runtime、任务调度、审批挂起、长任务执行和恢复。这里建议采用 **LangGraph JS 作为主执行引擎**，以支持单 Agent 推理、任务分解、多轮工具执行和执行状态追踪；同时在异步任务层面配合 BullMQ，后续长流程再升级到 Temporal。文档明确要求支持可视化工作流节点、单 Agent 执行、多 Agent 预留、长任务异步执行、checkpoint、任务恢复，以及审批通过后继续执行等能力，这些都说明运行时必须是“状态化”的，而不是简单函数调用。

### 5.3.4 工具与协议层

工具与协议层负责标准化接入企业内部 API、MCP 服务和外部工具，并提供统一治理。这里建议建设独立的 `Tool Gateway` 与 `Tool Registry`，让 Agent 只能通过网关调用工具，而不能直接访问企业系统。文档要求工具支持注册、分类、参数定义、版本管理、权限配置、风险等级定义，同时在治理上支持调用权限校验、请求参数校验、限流、超时、重试、熔断，以及对写数据库、发消息、创建工单、修改订单、调用代码执行器等高风险工具进行审批、沙箱、参数白名单、结果确认和审计。这个层级显然必须由中台自研掌控。

### 5.3.5 知识与记忆层

知识与记忆层是企业 AI 中台的核心能力之一。文档要求平台支持 PDF、Word、Excel、Markdown、HTML、企业 Wiki、数据库表/视图、业务系统内容接口和对象存储文件的接入，并具备文档解析、表格提取、智能切片、向量索引、关键词索引、混合检索、重排序、引用溯源、增量更新和权限继承。技术上建议拆分为 `Knowledge Ingestion Service`、`Retrieval Service` 和 `Memory Service` 三类服务：前者负责接入、解析、切片、向量化和索引；中者负责查询改写、混合召回、权限过滤、精排和引用打包；后者负责会话记忆、用户记忆、任务记忆和长期记忆。

在存储上，推荐使用 PostgreSQL 承载知识元数据、权限映射和记忆元数据；使用 pgvector 或 Milvus 承载向量；使用 OpenSearch 提供 BM25 与过滤能力；使用对象存储保存文档原件与解析产物。之所以不建议完全依赖第三方 RAG 框架，是因为文档特别强调“权限继承”“未授权内容不参与召回”“引用溯源”“文档版本覆盖”等企业化能力，这些能力必须和平台权限、审计体系深度结合。

### 5.3.6 模型服务层

模型服务层建议建设独立的 `Model Gateway`，由其统一承接公有云大模型、私有化部署模型、Embedding 模型、Reranker 模型和专用小模型。文档明确要求模型层支持统一注册、统一调用协议、智能路由、故障处理与降级、灰度发布、A/B 测试、Token 消耗统计、模型成本估算、部门级成本分账、应用级配额控制和用户级调用上限配置。

因此，模型层不应由应用或 Agent 直接调用厂商 SDK，而应通过统一模型网关进行调用。技术上建议用 NestJS 实现网关，对上暴露统一接口，对下适配不同模型提供方或私有推理服务。这样可以统一做路由、熔断、配额、成本统计、灰度策略和日志审计，符合平台型建设目标。

### 5.3.7 控制与治理层

控制与治理层负责身份权限、策略引擎、内容安全、审批和审计，是企业 AI 中台能否上线的关键。文档要求平台对接企业统一身份体系，支持单点登录、OAuth/OIDC、LDAP/AD、组织架构同步；支持多租户、部门管理、用户与角色管理、应用归属管理；对应用、模型、知识库、工具、工作流和审计视图进行 RBAC/ABAC 授权；并支持敏感词过滤、Prompt Injection 检测、越权访问检测、输出脱敏、高风险操作审批和事实性偏离告警。

因此，建议在这一层拆分 `auth-service`、`policy-service`、`approval-service`、`guardrail-service` 和 `audit-service`。其中身份认证尽量复用企业现有 IAM/SSO，不自建基础身份系统；权限控制采用 Casbin 或 OPA；安全策略和审批流由平台统一托管；审计服务负责完整记录“谁在什么时间发起了什么请求、调用了哪个模型、检索了哪些知识、调用了哪些工具，以及基于哪些上下文生成了什么结果”。

### 5.3.8 观测运营层

观测运营层负责日志、链路追踪、效果评测、反馈分析和成本看板。文档要求平台记录用户请求日志、模型调用日志、检索日志、工具调用日志、工作流执行日志、Agent 执行轨迹和审批日志，并支持按单次请求查看从“用户输入 → 权限校验 → 检索 → 模型调用 → 工具调用 → 输出结果”的完整链路，同时提供请求量、成功率、平均响应时间、工具调用成功率、引用率、差评率、应用活跃度，以及模型成本趋势、部门成本排行、应用成本排行、用户成本排行和高成本异常告警。

技术上建议采用 OpenTelemetry 做 trace，Prometheus 做 metrics，Grafana 做看板，Loki/ELK 做日志检索，并对 AI 特有埋点进行标准化，包括 app_id、tenant_id、model_id、prompt_version、retrieval_hit_docs、tool_calls、token_in/token_out、latency、cost 等字段。这样既能复用企业现有可观测基础设施，也能补齐 AI 特有指标。文档同样强调应复用现有日志平台/监控平台，由 AI 中台补充特有日志与指标。

* `portal-web`
* `app-config-service`
* `metadata-service`

### 5.4.2 运行面服务

运行面负责请求执行和能力供给，建议包括：

* `chat-gateway`

* `memory-service`

治理与运营负责企业级安全与运营支撑，建议包括：

## 5.5 技术选型说明

从你偏好的研发风格看，最合适的方案不是“全部自研”，也不是“全部押在一个 Agent 框架上”，而是分层取舍。

第一，**前后端统一 TypeScript**。这能显著降低系统复杂度，特别是在应用层、工作流配置层、工具 schema、前后端对象模型、权限模型和埋点模型都需要高度一致的情况下，TS 全栈有明显优势。

第二，**运行时复用成熟 Agent 框架**。文档对 Agent Runtime 的诉求是单 Agent 推理执行、任务分解、多轮工具执行、执行状态追踪、长任务恢复和多 Agent 预留。LangGraph 在这类状态流场景更合适，因此适合作为运行时核心。

第三，**平台治理能力必须自研**。模型网关、知识权限继承、工具治理、审批、审计、PromptOps / EvalOps、观测与成本，都是企业级平台价值所在，也是文档反复强调的重点。如果把这些能力交给第三方框架，后期往往很难适配企业权限体系、审批体系和审计体系。

---

## 5.6 分阶段实施建议

文档已明确给出三阶段建设路径，因此架构实现上也应按阶段逐步演进，而不是一开始就追求“全量中台”。

第一阶段建议聚焦“知识问答 MVP”，优先建设模型网关基础版、知识中枢基础版、应用交付基础版、基础权限控制以及基础日志与审计能力，先把制度、产品手册、FAQ 等高频低风险场景跑通。

第二阶段扩展到“工具型智能助手”，新增工具中心、单 Agent 执行能力、工作流编排基础版、会话记忆、PromptOps / EvalOps 初版和审批机制，使平台从“会回答”升级到“会办事”。

第三阶段再建设“流程自动化与多智能体”，引入多 Agent 协作、长任务运行时、深度策略治理、全链路评测与成本治理和高级 Memory 能力，支撑复杂任务、长链路自动化与多角色协作。

## 5.7 本章结论

综上，建议本项目采用 **“Next.js + NestJS + LangGraph JS + PostgreSQL/pgvector + Redis + OpenSearch + Object Storage”** 的总体技术方案，以 TypeScript 全栈统一研发语言，以 LangGraph 承接智能体与工作流运行时，以自研中台能力承接模型网关、知识治理、工具治理、权限治理、审计和运营观测。

这一路线与文档的建设目标、建设原则、能力范围、系统边界和分阶段实施路径是一致的：既满足“复用优先”的要求，又能够保证“平台优先”和“安全前置”的企业级落地能力。
