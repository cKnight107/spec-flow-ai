
# 企业 AI 中台建设需求说明书（初稿 V1.0）

## 1. 文档概述

### 1.1 文档名称

企业 AI 中台建设需求说明书

### 1.2 文档目的

本文档用于明确企业 AI 中台的建设背景、目标、范围、总体架构、核心功能需求、非功能要求、实施路径及验收标准，作为产品设计、技术架构、研发实施、测试验收及项目管理的统一依据。

### 1.3 适用范围

本文档适用于以下相关角色：

* 项目发起人 / 管理层
* 产品经理
* 技术架构师
* 后端研发 / 前端研发 / 算法研发 / 数据研发
* 测试团队
* 安全与运维团队
* 业务系统对接团队

### 1.4 参考目标

建设一个面向企业内部多业务场景的 AI 中台，统一支撑以下能力：

* 大模型统一接入与调度
* 企业知识接入与 RAG 检索增强
* 工具标准化接入与 Agent 编排
* Prompt/评测/反馈闭环
* 多应用快速交付
* 权限、安全、审计与观测治理

### 1.5 术语说明

**LLM**：大语言模型
**RAG**：检索增强生成
**Agent**：具备推理、规划、工具调用和任务执行能力的智能体
**Workflow**：规则化、可编排的业务流程
**MCP**：模型上下文协议，用于工具/资源标准化接入
**A2A**：Agent 与 Agent 之间的交互与协作协议
**Memory**：用于保留上下文、用户偏好和任务状态的记忆机制
**PromptOps**：提示词管理与优化体系
**EvalOps**：评测、反馈、回归和效果优化体系
**Guardrails**：输入输出安全控制与策略约束机制

## 2. 项目背景与建设目标

### 2.1 项目背景

随着大语言模型能力的成熟，企业在知识问答、办公协同、业务助手、流程自动化等方面开始出现大量 AI 应用需求。但当前企业内部普遍面临以下问题：

1. 模型接入分散，能力无法统一管理
   各团队直接调用不同厂商或不同部署形态的模型，接口不统一、策略不统一、成本不可控。

2. 企业知识孤岛严重，AI 缺乏业务上下文
   内部知识分散在文档、Wiki、数据库、业务系统中，大模型无法直接理解企业内部事实，容易产生幻觉。

3. AI 应用重复建设，难以规模化复制
   各业务部门单独建设问答助手或智能流程，技术栈分散，重复造轮子，交付效率低。

4. 缺乏统一的工具接入与任务执行机制
   AI 大多停留在“对话”阶段，无法安全可靠地调用企业内部系统完成实际工作。

5. 缺乏完善的安全、权限、审计与监控体系
   数据权限、敏感信息、模型成本、工具调用风险、回答可追溯性等缺乏统一治理。

因此，需要建设一个统一的企业 AI 中台，沉淀企业 AI 公共能力，支撑各业务线快速、安全、可控地构建 AI 应用。

### 2.2 建设目标

#### 2.2.1 业务目标

* 提升员工获取制度、产品、流程等知识的效率
* 减少重复性查询、填报、检索、摘要等人工操作
* 将 AI 从问答工具升级为可执行任务的业务助手
* 通过统一中台能力，缩短 AI 应用建设周期

#### 2.2.2 平台目标

* 统一模型接入、路由、配额和成本管理
* 统一知识接入、索引、检索、溯源和更新
* 统一工具接入、调用权限和 Agent 编排执行
* 统一 Prompt 管理、评测验证与反馈优化
* 统一应用发布、监控、日志审计和安全治理

#### 2.2.3 技术目标

* 支持多模型、多知识源、多应用、多租户
* 支持标准化工具接入协议与运行时治理
* 支持可观测、可评测、可审计、可扩展的架构
* 支持从 RAG 问答到任务自动化的分阶段落地

### 2.3 建设原则

* 复用优先：尽量复用现有模型、数据库、向量库、身份体系和业务系统
* 平台优先：公共能力沉淀到中台，业务层尽量轻
* 数据优先：优先解决知识接入、权限继承和数据质量问题
* 安全前置：权限、脱敏、审计、审批机制必须前置设计
* 分阶段建设：先做高频、低风险、可验证场景，再做复杂自治场景
* 配置优先：尽量用配置、编排和策略驱动，减少场景级硬编码

## 3. 建设范围与边界

### 3.1 本期建设范围

本期企业 AI 中台建设范围包括以下八大能力域：

1. 模型网关与路由中心
2. 知识与记忆中心
3. 智能体与工作流中心
4. 工具与协议中心（MCP/API/A2A）
5. PromptOps / EvalOps 中心
6. 应用交付中心
7. 身份权限与治理中心
8. 观测运营与成本中心

### 3.2 本期不包含范围

以下内容原则上不作为本期建设重点：

* 通用大模型预训练平台
* 大规模模型微调训练平台
* 完整的企业级 BPM 替代系统
* 企业所有业务系统的全量自动化改造
* 面向外部生态的开放插件市场
* 全公司范围自治型多智能体协作体系

### 3.3 与现有系统边界

企业 AI 中台与现有系统关系如下：

* **与 IAM/SSO 系统**：复用现有身份认证与组织体系，不自建基础身份系统
* **与 API 网关**：复用现有网关能力，AI 中台负责 AI 能力路由与工具调用治理
* **与数据中台**：不替代数据中台，重点做 AI 面向知识和语义检索的能力封装
* **与 BPM/流程引擎**：复杂传统审批流仍由 BPM 承担，AI 中台可作为智能节点或前置助手
* **与日志平台/监控平台**：复用企业现有可观测基础设施，补充 AI 特有日志与指标

## 4. 用户角色与使用场景

### 4.1 用户角色

#### 4.1.1 平台管理员

负责平台级配置与治理，包括：

* 模型接入配置
* 租户与组织管理
* 权限策略管理
* 工具中心管理
* 安全策略配置
* 监控与审计查看

#### 4.1.2 应用管理员

负责具体 AI 应用的配置和发布，包括：

* 创建 AI 应用
* 绑定知识库、模型、Prompt、工作流、工具
* 配置发布渠道
* 查看应用效果与反馈

#### 4.1.3 知识管理员

负责知识内容和知识库管理，包括：

* 文档上传与接入
* 文档标签与权限映射
* 解析、切片、清洗规则配置
* 知识更新和失效管理

#### 4.1.4 开发者 / 集成人员

负责业务系统集成与工具开发，包括：

* 封装业务 API 为标准工具
* 集成前端组件和 SDK
* 对接业务系统和消息渠道
* 扩展工作流节点能力

#### 4.1.5 普通业务用户

使用 AI 应用完成问答、辅助决策和任务处理，包括：

* 查询制度、流程、产品知识
* 调用助手获取业务数据
* 发起任务、审批、查询与处理

#### 4.1.6 安全 / 审计人员

负责风险审计和合规检查，包括：

* 查看调用日志和审计链路
* 审核高风险工具调用
* 配置敏感策略和例外规则
* 跟踪异常行为和事件

---

### 4.2 核心业务场景

#### 场景一：制度知识问答

用户通过企业门户或 IM 助手提问制度相关问题，系统根据权限检索制度文件，返回答案和引用来源。

#### 场景二：销售业务助手

销售人员查询客户信息、订单状态、库存情况，系统调用 CRM/订单系统工具返回结果，并支持根据业务规则生成行动建议。

#### 场景三：IT 运维助手

运维人员查询告警、设备状态、工单处理建议，系统结合知识库和运维工具提供信息和自动化建议。

#### 场景四：HR 招聘助手

HR 查询候选人进度、岗位 JD、面试安排建议，系统支持会话记忆与流程辅助。

#### 场景五：管理报表分析助手

管理者上传报表或选择数据源，系统生成摘要、异常分析和建议，必要时调用数据分析工具执行查询。

#### 场景六：流程型 Agent 助手

用户发起任务型需求，如“查询订单后生成汇总并通知负责人”，系统通过工作流或 Agent 编排完成多步骤执行。

## 5. 总体架构设计

### 5.1 总体架构目标

企业 AI 中台总体架构应满足以下要求：

* 对上支撑多业务应用、多接入渠道
* 对中沉淀公共 AI 能力
* 对下屏蔽模型和数据源差异
* 横向具备权限、安全、审计、观测和成本治理能力

### 5.2 架构分层

平台总体分为八层：

1. 接入层
2. 应用层
3. 编排与执行层
4. 工具与协议层
5. 知识与记忆层
6. 模型服务层
7. 控制与治理层
8. 观测运营层

### 5.3 模块职责概述

#### 5.3.1 接入层

负责 Web、企业微信、飞书、钉钉、OpenAPI、SDK 等接入。

#### 5.3.2 应用层

负责构建各类 AI 应用，如问答助手、业务助手、数据分析助手等。

#### 5.3.3 编排与执行层

负责 Workflow、Agent Runtime、任务调度、审批挂起、长任务执行和恢复。

#### 5.3.4 工具与协议层

负责标准化接入企业内部 API、MCP 服务、外部工具和多 Agent 协作协议。

#### 5.3.5 知识与记忆层

负责企业知识加工、检索增强和多层记忆能力。

#### 5.3.6 模型服务层

负责统一模型调用、路由、熔断、灰度和成本管理。

#### 5.3.7 控制与治理层

负责身份权限、策略引擎、内容安全、审批和审计。

#### 5.3.8 观测运营层

负责日志、链路追踪、效果评测、反馈分析和成本看板。

## 6. 功能需求

## 6.1 模型网关与路由中心

### 6.1.1 模块目标

统一接入多种模型能力，屏蔽底层差异，实现稳定、可控、低成本的模型服务供给。

### 6.1.2 功能需求

#### 6.1.2.1 多模型统一接入

系统应支持接入以下模型类型：

* 公有云大模型
* 私有化部署开源模型
* Embedding 模型
* Reranker 模型
* 专用小模型
* 多模态模型（按后续阶段扩展）

系统应提供统一的模型注册配置，包括：

* 模型名称
* 模型类型
* 服务地址
* 认证方式
* 输入输出协议
* 最大 token
* 支持能力标签
* 适用场景标签

#### 6.1.2.2 统一调用协议

平台应为上层应用屏蔽不同模型厂商的调用差异，统一请求结构与响应结构。

统一能力至少包括：

* 文本生成
* 对话生成
* 向量生成
* 重排序
* 函数调用
* 流式输出

#### 6.1.2.3 智能路由

平台应支持基于以下维度进行路由：

* 应用场景
* 任务类型
* 成本优先级
* 时延优先级
* 模型能力标签
* 部门策略
* 风险等级

#### 6.1.2.4 故障处理与降级

平台应支持：

* 超时控制
* 熔断
* 自动重试
* 主备模型切换
* 降级到低成本模型或默认回复策略

#### 6.1.2.5 灰度发布与 A/B 测试

平台应支持：

* 新模型灰度上线
* 指定流量比例切分
* 指定应用灰度
* 对比评测指标回收

#### 6.1.2.6 成本与配额

平台应支持：

* Token 消耗统计
* 模型成本估算
* 部门级成本分账
* 应用级配额控制
* 用户级调用上限配置

### 6.1.3 权限要求

* 仅平台管理员可新增或下线模型
* 应用管理员仅可绑定有权限的模型
* 高成本模型应支持额外审批或白名单使用

### 6.1.4 日志与审计要求

每次模型调用至少记录：

* 调用时间
* 调用应用
* 用户标识
* 模型名称
* 输入摘要
* 输出摘要
* Token 消耗
* 路由策略
* 调用时延
* 调用状态

## 6.2 知识中枢（RAG）

### 6.2.1 模块目标

统一承载企业内部知识的接入、加工、索引、检索、精排和溯源，提升回答准确性和可信度。

### 6.2.2 功能需求

#### 6.2.2.1 多源知识接入

系统应支持以下知识源接入：

* PDF
* Word
* Excel
* Markdown
* HTML
* 企业 Wiki
* 数据库表/视图
* 业务系统内容接口
* 对象存储中的文件

#### 6.2.2.2 文档解析与清洗

系统应支持：

* 文档解析
* 文本抽取
* 表格提取
* 去重
* 去噪
* 特殊字符清洗
* 敏感信息脱敏
* 元数据提取

#### 6.2.2.3 智能切片

系统应支持：

* 固定长度切片
* 按段落切片
* 按标题层级切片
* 语义切片
* 重叠窗口配置
* 父子块检索策略扩展能力

#### 6.2.2.4 索引与存储

系统应支持：

* 向量索引
* 关键词索引
* 元数据索引
* 文档版本索引
* 权限标签索引

#### 6.2.2.5 混合检索

系统应支持：

* 向量检索
* BM25 关键词检索
* 向量 + 关键词混合召回
* 元数据过滤
* 权限过滤
* 时间过滤
* 文档类型过滤

#### 6.2.2.6 重排序

系统应支持检索结果二次精排，提高召回结果相关性。

#### 6.2.2.7 引用溯源

系统应支持在回答中展示以下信息：

* 文档名称
* 来源链接
* 页码或章节位置
* 引用片段摘要

#### 6.2.2.8 增量更新

系统应支持：

* 定时同步
* 事件触发同步
* 增量索引更新
* 失效文档回收
* 文档版本覆盖

#### 6.2.2.9 权限继承

系统应支持：

* 继承源系统权限
* 根据组织、角色、应用控制知识访问范围
* 未授权内容不参与召回或不展示原文

### 6.2.3 数据对象

建议至少定义以下对象：

* 知识库
* 知识源
* 文档
* 文档版本
* chunk
* embedding 向量
* 索引任务
* 权限映射规则
* 标签元数据

### 6.2.4 审计要求

记录以下行为：

* 文档上传
* 文档删除
* 文档解析失败
* 文档更新
* 检索请求
* 检索命中结果
* 引用结果

## 6.3 记忆中心

### 6.3.1 模块目标

为对话、任务和用户提供持续上下文支撑，使 AI 从单轮问答升级为可持续协同的智能助手。

### 6.3.2 功能需求

#### 6.3.2.1 会话记忆

系统应支持：

* 保存多轮对话历史
* 自动摘要长会话
* 控制上下文注入长度
* 选择性保留关键信息

#### 6.3.2.2 用户记忆

系统应支持记录与管理：

* 用户偏好
* 用户常用上下文
* 用户角色与岗位辅助信息
* 经授权的个性化设置

#### 6.3.2.3 任务记忆

系统应支持：

* 保存任务执行状态
* 保存中间变量
* 支持中断后恢复
* 支持跨天续办任务

#### 6.3.2.4 长期记忆

系统应支持：

* 从对话中抽取长期有效信息
* 设置记忆有效期
* 手动修正和删除记忆
* 控制哪些记忆可被应用使用

#### 6.3.2.5 安全控制

系统应支持：

* 敏感信息不进入长期记忆
* 记忆访问权限控制
* 用户可查看或清理个人记忆
* 应用间记忆隔离

### 6.3.3 审计要求

记录：

* 记忆创建
* 记忆更新
* 记忆删除
* 记忆命中
* 记忆注入到上下文的行为

---

## 6.4 智能体与工作流中心

### 6.4.1 模块目标

实现任务编排、流程执行、工具调用和 Agent 协作，使平台具备“会办事”的能力。

### 6.4.2 功能需求

#### 6.4.2.1 工作流编排

系统应支持可视化配置以下节点：

* 用户输入节点
* Prompt 节点
* 条件判断节点
* 检索节点
* 模型调用节点
* 工具调用节点
* 并行节点
* 循环节点
* 人工审批节点
* 输出节点

#### 6.4.2.2 Agent Runtime

系统应支持：

* 单 Agent 推理与执行
* 基于目标进行任务分解
* 工具选择与参数组装
* 多轮工具执行
* 执行状态追踪

#### 6.4.2.3 多智能体协作

系统应预留或支持：

* 规划者 Agent
* 执行者 Agent
* 审核者 Agent
* 多 Agent 消息传递
* 协作链路追踪

#### 6.4.2.4 异步执行与任务恢复

系统应支持：

* 长任务异步执行
* 任务暂停
* 任务重试
* checkpoint
* 任务恢复

#### 6.4.2.5 审批机制

系统应支持：

* 高风险工具调用审批

## 10. 验收标准

### 10.1 平台级验收

* 平台可统一接入至少 2 类以上 LLM
* 平台可接入至少 2 类知识源
* 平台可发布至少 3 个 AI 应用
* 平台具备统一的日志审计与权限控制能力

### 10.2 RAG 能力验收

* 文档可完成解析、切片、索引和检索
* 回答可展示引用来源
* 文档权限不穿透
* 文档更新后支持增量索引

### 10.3 Agent / Workflow 能力验收

* 可配置完整工作流并执行
* 支持工具调用与轨迹记录
* 支持高风险节点审批
* 支持失败重试与中断恢复

### 10.4 治理验收

* 非授权用户不可访问受限应用或知识
* 审计人员可追溯单次请求的关键链路
* 支持敏感内容和基础注入攻击拦截

### 10.5 运营验收

* 可查看调用量、时延、成本、反馈
* 可追踪 bad case 并导出
* 可进行基础效果评测与对比

## 11. 风险与依赖

### 11.1 项目风险

* 源系统权限不清晰导致知识权限继承困难
* 文档质量差导致检索效果不佳
* 业务系统接口不标准导致工具接入成本高
* 高风险场景对审批和审计要求高，影响上线节奏
* 模型成本与调用量增长过快造成预算压力

### 11.2 外部依赖

* 企业统一身份认证系统
* 业务系统 API 能力
* 文档/Wiki/数据库等知识源可接入性
* 监控、日志、审计基础设施
* 向量数据库和对象存储基础设施
